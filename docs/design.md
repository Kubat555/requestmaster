## 1. Зачем

**[владелец]** Текущий Postman медленный, платный для команды и постоянно добавляет ненужное. Нужна собственная
бесплатная альтернатива: на Rust, быстрая, с современным красивым и удобным интерфейсом и анимациями, под Windows 11.
База: папки, переменные, скрипты, импорт текущих данных из Postman и экспорт обратно.

Успех первой версии: владелец переносит свои рабочие коллекции из Postman и ведёт ежедневную работу в RequestMaster,
не открывая Postman.

## 2. Цели, не-цели, анти-цели

### Цели первой версии (этапы 0–2)
1. Импорт коллекций Postman (Collection v2.1 JSON), окружений и глобальных переменных; экспорт в те же форматы.
2. Дерево коллекций с вложенными папками; создание, переименование, перемещение, удаление, дублирование.
3. Отправка HTTP-запросов: метод, URL, query-параметры, path-переменные, заголовки, тело
   (raw, x-www-form-urlencoded, form-data с файлами, binary file, GraphQL как обычный POST), авторизация.
4. Переменные четырёх областей (global, collection, environment, local) и подстановка `{{var}}` как в Postman.
5. Pre-request и test-скрипты на JavaScript, совместимые с `pm.*`; скрипты хранятся и исполняются дословно,
   без перевода в другой API.
6. Быстрый запуск и отзывчивость (измеримые цели — раздел 10).
7. Собственный визуальный стиль и система анимаций с первого экрана, а не «потом».
8. Полностью локальная работа: без аккаунта, без облака, без телеметрии.

### Не-цели первой версии (отложено, раздел 12)
Collection Runner и CLI, OAuth 2.0-потоки получения токена, WebSocket/SSE/gRPC, HTTP/3,
NTLM/клиентские сертификаты, командный git-формат файлов, шифрование секретов, импорт OpenAPI/cURL,
палитра команд, светлая тема, кастомный заголовок окна и Mica.

### Анти-цели (провал, даже если технически работает)
- Требуется регистрация или сеть для запуска.
- Импорт «прошёл», но запросы или скрипты после него молча не работают. Всё неподдержанное должно быть названо
  в отчёте импорта.
- Данные теряются при цикле «импорт → экспорт»: поля Postman, которые приложение не понимает, должны сохраняться.
- Интерфейс подтормаживает на вводе или анимации задерживают появление данных.
- Скрипт из чужой коллекции получает доступ к файлам или сети в обход приложения.

## 3. Технологии

| Часть | Выбор | Пометка |
|---|---|---|
| Ядро (вся логика) | Rust, cargo workspace | **[владелец]** — Rust |
| Окно и интерфейс | Tauri 2 (линия 2.12.x, не 3.0-alpha), WebView2 | **[моё решение]** |
| Фронтенд | Svelte 5 + TypeScript, сборка Vite | **[моё решение]** |
| Редактор кода | CodeMirror 6 | **[моё решение]** |
| HTTP | `reqwest` 0.13 за собственным trait `HttpEngine` | **[моё решение]** |
| Движок скриптов | `rquickjs` 0.14.0 (QuickJS-NG 0.16.2), встроен в ядро; библиотеки скриптов — chai 4.4.1 и lodash 4.18.1 | **[моё решение]** |
| Хранилище | один файл SQLite (`rusqlite`, bundled) в `%LOCALAPPDATA%\RequestMaster\` | **[моё решение]** |
| Асинхронность | `tokio` | **[моё решение]** |

### Что значит «на Rust» — честно
Интерфейс в Tauri пишется на Svelte/TypeScript: это около половины кода проекта или больше. На Rust — всё ядро:
HTTP, форматы Postman, переменные, скрипты, хранилище. Причина выбора: только веб-стек сегодня даёт одновременно
отточенные анимации, зрелый редактор кода (подсветка JSON/JS, сворачивание, поиск) и готовую доступность.
Альтернатива «всё на Rust» — GPUI + gpui-component: запуск быстрее и памяти меньше, но опубликованный crate `gpui`
устарел (0.2.2, октябрь 2025), API нестабилен, анимации и редактор пришлось бы доводить самим — существенно дольше.
Остальные Rust-GUI (Slint, iced, egui, Dioxus native, Freya, Makepad) отклонены: нет готового редактора кода
нужного уровня либо незрелость. **Решение согласовано владельцем 2026-11-12 (раздел 15, п. 1).**

Правило, которое делает «ядро на Rust» проверяемым: в TypeScript нет разбора Postman-JSON, подстановки переменных,
отправки запросов и исполнения скриптов. Crates ядра не зависят от Tauri, собираются и тестируются без окна.

### Почему остальные выборы такие
- **reqwest, а не свой движок на hyper.** Свой движок даёт разбивку DNS/TCP/TLS и сырые байты, но это тысячи строк
  и много граничных случаев. В первой версии показываем общее время и время до первого байта. Trait `HttpEngine`
  позволяет позже заменить реализацию, не трогая остальное. Редиректы обрабатываем сами (reqwest с выключенным
  авто-redirect), чтобы показывать цепочку. TLS — rustls с провайдером `ring`: подтверждено на этапе 0 —
  собирается под MSVC без NASM/CMake, `aws-lc-rs` в дереве нет; в `reqwest` 0.13 это feature `rustls-no-provider`
  и установка провайдера `ring` до сборки клиента (результаты этапа 0, §2.2).
- **rquickjs, а не V8/Boa/WebView.** +1–2 МБ к размеру (этап 2: exe вырос на 1,58 МиБ, установщик — на 0,57 МиБ),
  рантайм с прелюдией создаётся примерно за миллисекунду, async/await есть.
  V8 — десятки МБ. Исполнять скрипты в WebView небезопасно и привязывает движок к окну.
- **SQLite, а не файлы в git.** В требованиях локальная работа; файловый формат «файл на запрос» тянет за собой
  наблюдение за диском, гонки записи, правила имён файлов Windows. Он вынесен в отдельный поздний подпроект
  (владелец подтвердил 2026-11-12: командная работа — позже, раздел 15, п. 2).

## 4. Архитектура

```
<корень репозитория>/
  crates/
    rqm-model/      доменная модель: Collection, Folder, Request, Environment, Variable, Auth, Body
    rqm-postman/    serde-структуры Postman v2.1 + environment/globals; конвертация <-> rqm-model
    rqm-vars/       области переменных, подстановка {{var}}, динамические {{$...}}
    rqm-http/       trait HttpEngine + реализация на reqwest; редиректы, cookies, декомпрессия, отмена
    rqm-script/     rquickjs, прелюдия pm.* (JS), песочница, пределы времени, памяти и стека, сторож
    rqm-store/      SQLite: чтение/запись модели и состояния приложения
    rqm-runner/     сценарий «отправить запрос»: переменные -> pre-request -> подстановка -> HTTP -> test
  src-tauri/       тонкая оболочка: команды Tauri (событий в UI нет); логики нет
  ui/              Svelte 5 + TypeScript
```

Зависимости направлены в одну сторону: `src-tauri` → `rqm-runner` → (`rqm-http`, `rqm-script`, `rqm-vars`, `rqm-store`)
→ `rqm-model`; `rqm-postman` → `rqm-model`. Ни один `rqm-*` не зависит от Tauri.

### Crate `rqm-script` (этап 2)
Зависит только от `rquickjs`, `rqm-vars`, `serde_json`, `tokio-util` — не от `rqm-http`, `rqm-store`,
`rqm-model`, `rqm-runner`. Устройство:
- `engine.rs` — поток ОС на задание (стек 16 МиБ), `Runtime` и `Context` на каждый скрипт, обёртка скрипта
  `(async()=>{…})()` (номера строк совпадают с редактором), цикл заданий, чтение ошибок, сторож;
- `budget.rs` — секундомер исполнения JavaScript (пауза на время ожидания хоста), срок для сторожа, отмена;
- `host.rs`, `variables.rs` — примитивы хоста (консоль, тесты, переменные, тело ответа, таймеры, сеть, запрос) и
  журнал изменений переменных; **каждый предел проверяет Rust**, прелюдия — только удобство;
- `bundle.rs` — собранные JS-файлы (`prelude/built/{prelude,chai,lodash}.js`, коммитятся; собирает только
  `npm run build` в `crates/rqm-script/prelude/`, `cargo` Node не вызывает), байткод в `OnceLock`;
- `api.rs` — таблица API (`prelude/src/api.json`) и поиск неподдержанного в тексте скрипта;
- `text.rs` — обрезка по границе символа, строки JS с одиночным суррогатом.

Сеть скрипту даёт trait `Host`, который реализует `rqm-runner` (`script_host.rs`) поверх `HttpEngine`.

### Сценарий «Send» (`rqm-runner`)
1. Собрать области переменных: global < collection < environment < local (побеждает самая узкая).
2. Выполнить pre-request скрипты: коллекция → папки от внешней к внутренней → запрос. Скрипты исполняются,
   только если включено «Выполнять скрипты» и коллекции дано согласие (раздел 11); иначе отправка идёт без них,
   с предупреждением. Ошибка pre-request любого уровня: остальные pre-request не исполняются, запрос не
   отправляется, test не исполняются. `pm.execution.skipRequest()` — запрос не отправляется, ошибкой не считается.
3. Подставить переменные в URL, заголовки, тело, auth; разрешить унаследованный auth (подъём к родителям;
   отсутствие auth = наследовать, `noauth` = явно без авторизации).
4. Отправить через `HttpEngine`.
5. Выполнить test-скрипты в том же порядке: коллекция → папки → запрос. Ошибка test-скрипта ответ не отнимает,
   следующие test-скрипты цепочки исполняются.
6. Вернуть ответ, результаты тестов, вывод консоли, ошибки скриптов, изменения переменных.
7. Оболочка записывает изменения переменных в базу — один раз, когда отправка завершилась (в том числе ошибкой
   или отменой), дельтой поверх свежего чтения, — и пишет запись истории.

Каждый запуск имеет токен отмены; кнопка Cancel прерывает и сеть, и скрипт.

### Потоки
- `tokio` multi-thread runtime — сеть и ввод-вывод.
- Скрипты исполняются в выделенном потоке ОС (не в задаче tokio): экземпляр QuickJS однопоточный. Обращения
  скрипта к хосту (`pm.sendRequest`, таймеры) — сообщения в tokio-ядро через каналы.
- `pm.sendRequest` использует тот же `HttpEngine`, что и обычная отправка.

## 5. Данные

### Доменная модель и Postman-модель разведены
- `rqm-postman` читает Collection v2.1 терпимо: полиморфные места (`request` и `url` строкой или объектом,
  `header` строкой или массивом, `script.exec` строкой или массивом) разбираются в любом виде, неизвестные ключи
  и типы импорт не роняют. Готовый crate `postman_collection` не используем: он молча теряет неизвестные поля.
- `rqm-model` — то, с чем работает приложение. Неизвестное не теряется за счёт правил P1–P4 **[моё решение]**
  (уточнение этапа 1A: вместо «мешка» неизвестных полей на каждом уровне зеркальных структур хранится исходный
  фрагмент целиком; результат тот же):
  - **P1.** У каждого узла (коллекция, папка, запрос, окружение) есть `postman_extra` — исходный JSON-объект
    этого узла из Postman без потомков (`item`) и имени (`name`); для запроса — элемент целиком вместе
    с вложенным `request`. В нём остаются ID, `_exporter_id`, неподдержанные ключи `protocolProfileBehavior`,
    неподдержанные типы auth, `script.packages`, сохранённые примеры ответов и т.п. У узла, созданного
    в приложении, `postman_extra` пуст.
  - **P2.** Экспорт узла начинается с копии `postman_extra`. Типизированное поле (`url`, `header`, `body`,
    `auth`, `event`, `variable`, `protocolProfileBehavior`, `method`, `values`) записывается заново, только если
    оно изменилось: если разбор исходного значения даёт то же, что лежит в модели, остаётся исходное значение
    дословно — вместе с явным `null`, порядком ключей и неизвестными вложенными ключами.
  - **P3.** У строк списков (параметр, заголовок, переменная, поле формы) свой `postman_extra` — исходный
    объект строки целиком. Когда список изменён и пишется заново, каждая строка строится от своего исходного
    объекта, и переписывается только изменившийся ключ (так у нетронутых строк остаются `description`, ID,
    числа, булевы значения и `null`).
  - **P4.** Скрипт в модели — одна строка. При изменении скрипта в исходном событии заменяется только
    `script.exec`, остальные ключи события сохраняются.
- `protocolProfileBehavior` разбирается частично **[моё решение]**: ключи `followRedirects`, `maxRedirects`,
  `strictSSL` и `disableBodyPruning` становятся настройками запроса (вкладка Settings) и работают;
  `disabledSystemHeaders` становится списком отключённых автозаголовков запроса (раздел 7); остальные ключи
  сохраняются в `postman_extra` и перечисляются в отчёте импорта как «настройка не применяется». На папке
  и коллекции не применяется ни один ключ — все перечисляются в отчёте.
- Унаследованные auth и скрипты в потомков не копируются — вычисляются при запуске.
- Ключи вне схемы, реально встреченные в экспорте владельца (этап 0): `_postman_id`, `_exporter_id`,
  `_collection_link`, у скриптов `packages` и `requests`, `protocolProfileBehavior` (ключ `disableBodyPruning`),
  `_postman_previewlanguage`. Все они возвращаются при экспорте без потерь (результаты этапа 0, §2.3;
  на этапе 1A — тесты на образце владельца, расхождений 0).
- Пробел с явным JSON `null` (результаты этапа 0, §2.3) закрыт на этапе 1A правилом P2: нетронутое поле
  экспортируется исходным значением дословно, поэтому `"auth": null`, `description: null` и `null` в значении
  переменной не превращаются в «поля нет». Если поле изменили в приложении, оно пишется заново по модели.

### Критерий экспорта
Не побайтовое совпадение, а: Postman открывает экспортированный файл; запросы, скрипты, переменные и auth работают
так же; ID и неизвестные поля сохранены. Автотест: «импорт → экспорт → семантическое сравнение JSON» на корпусе
реальных экспортов; расхождения допустимы только из явного списка (например, порядок ключей).

### Переменные
- Области и приоритет: global < collection < environment < local. Local живёт один запуск (`pm.variables.set`).
- Одно значение на переменную (как в файле экспорта Postman) **[моё решение]**; пара initial/current — вместе
  с командным форматом.
- Подстановка как в Postman: шаблон `{{имя}}`, имя — любые символы кроме фигурных скобок; сначала внутренние токены,
  повтор до 19 проходов (работают вложенные `{{a{{b}}}}` и значения, содержащие `{{...}}`); неразрешённый токен
  остаётся в тексте как есть; отключённые переменные пропускаются.
- Path-переменные: сегмент `/:id` заменяется значением из списка path-переменных запроса.
- Динамические в первой версии: `{{$guid}}`, `{{$randomUUID}}`, `{{$timestamp}}`, `{{$isoTimestamp}}`,
  `{{$randomInt}}`; новое значение на каждое вхождение.
- Тип `secret`: значение хранится в SQLite открыто, в интерфейсе замаскировано **[моё решение]**. При экспорте
  окружения значения выгружаются (иначе обратный переход в Postman теряет данные), с предупреждением в диалоге.

## 6. Импорт и экспорт

### Импорт (первая версия)
- Collection v2.1 JSON; environment JSON; globals JSON. Формат определяется автоматически по содержимому
  (`info.schema`, `_postman_variable_scope`). Можно перетащить несколько файлов сразу.
- Один шаг: перетащил → импортировано как новая коллекция/окружение → показан отчёт.
- Отчёт импорта перечисляет: неподдержанные типы auth; неприменяемые настройки запроса; наличие скриптов;
  ссылки на файлы (form-data, binary). С этапа 2 — запись «Не поддерживается в скриптах» (вид
  `unsupported_script_api`): вызовы `pm.*` и `require(...)`, которых нет в движке; определяются поиском по
  тексту скриптов, поэтому имя в комментарии или в строке тоже попадает в отчёт.
- Файлы из импортированной коллекции **[моё решение]**: путь сохраняется как есть, но файл помечен
  «не подтверждён» и не отправляется, пока пользователь не выберет его заново в интерфейсе. Относительные пути
  в первой версии не разрешаются (показываются как «файл не найден»).
- Globals **[моё решение]**: область одна, поэтому импорт сливает значения в существующие; при совпадении имён
  показывается список конфликтов и выбор «взять из файла / оставить текущие / отмена».
- Согласие на скрипты. Замысел спеки — вопрос «Разрешить скрипты этой коллекции?» при импорте (план этапа 2
  делал его блоком отчёта импорта, не отдельным окном). **[владелец]** (2026-11-18): вопроса нет —
  импортированная коллекция разрешена сразу, блока согласия в отчёте импорта нет. Согласие хранится не на
  коллекции, а в `app_state` (ключ `scripts_allowed`, раздел 5) и меняется галочкой «Разрешить скрипты этой
  коллекции» в её редакторе; запрещённая коллекция отправляет запросы без скриптов, с предупреждением и
  кнопкой «Разрешить».
- Парсер терпим к неизвестному: неизвестные поля и типы не роняют импорт, а сохраняются.

образца дампа не было, результаты этапа 0, §5), формат v3 YAML,

## 7. HTTP

Первая версия:
- методы: стандартные и произвольная строка;
- тело: raw (с языком: JSON, XML, HTML, Text, JavaScript), urlencoded, form-data (текст и файлы), binary file,
  GraphQL (`{query, variables}` как POST);
- обрезка тела **[моё решение]** (уточнение этапа 1A): у методов `GET`, `HEAD`, `COPY`, `PURGE`, `UNLOCK` тело
  не отправляется, как в Postman; настройка запроса `disableBodyPruning` это отменяет — тело уходит;
- auth: No Auth, Basic, Bearer, API Key (в заголовке или query), OAuth 2.0 — только поле с готовым токеном
  (токен добавляется в заголовок или в query, как выбрано в запросе), наследование от родителя. Остальные типы
  сохраняются и показываются как «не поддерживается»;
- редиректы: следование вкл/выкл, цепочка видна в ответе. Обязательно (этап 1): при переходе на другой origin
  снимать `Authorization` и `Cookie`; после смены метода на GET не повторять заголовки тела (`Content-Type`,
  `Content-Length`). Пробник этого не делал (результаты этапа 0, §6);
- cookies: общий jar, автоматически отправляются и сохраняются; простой просмотр и очистка;
- декомпрессия gzip / brotli / deflate / zstd; показывается размер. Распаковку делаем сами, авто-декомпрессия
  `reqwest` выключена: она удаляет `Content-Encoding`/`Content-Length` и не даёт размер «на проводе»
  (результаты этапа 0, §2.2);
- настройки приложения (общие): таймаут запроса, проверка SSL-сертификата, прокси (системный, заданный
  вручную или «без прокси» — соединение напрямую). Настройки запроса (переопределяют общие): следование
  редиректам, максимум редиректов, проверка SSL; отдельно — `disableBodyPruning` (обрезка тела, см. выше).
  Уточнения плана 2 части 3 **[моё решение]**: таймаут задаётся в миллисекундах, `0` — без ограничения,
  наибольшее значение — 3 600 000 (час); адрес прокси «вручную» проверяется при сохранении настроек (`http://`
  или `https://` с хостом) — при ошибке сохранение отклоняется и прежние настройки остаются; системный прокси —
  без PAC и WPAD; максимум редиректов запроса — целое 0–9999. Общих «следовать редиректам» и «максимум
  редиректов» нет — это настройки запроса;
- автозаголовки **[моё решение]**: `Host`, `User-Agent: RequestMaster/<версия>`, `Accept: */*`, `Accept-Encoding`,
  `Content-Type` по типу тела, `Content-Length`. Показаны во вкладке Headers отдельной группой, каждый можно
  переопределить. Отключить можно все, кроме `Host`, `Accept` и `Content-Length` (уточнение этапа 1A): `Host`
  и `Content-Length` ставит HTTP-стек, `Accept: */*` клиент `reqwest` дописывает всегда. Список отключённых
  автозаголовков хранится в запросе и переносится в Postman и обратно как
  `protocolProfileBehavior.disabledSystemHeaders`. `Postman-Token` и `Cache-Control` не добавляются;
- отмена запроса;
- в ответе: статус, общее время, время до первого байта, размер, заголовки, cookies, тело.

## 8. Скрипты

Раздел приведён к тому, что сделано на этапе 2; итоги — `2026-11-17-stage2-scripts-results.md`.

- На **каждый скрипт** создаётся свежий `Runtime` и `Context` QuickJS **[моё решение]** (а не один контекст на
  Send): глобальные имена JavaScript от скрипта к скрипту не переходят, как в Postman; между скриптами одной
  отправки переходят только переменные (включая local) и запрос. Замер: ~0,7 мс на скрипт.
- Прелюдия — JavaScript с реализацией `pm.*`, собирается esbuild из `crates/rqm-script/prelude/src`; собранные
  файлы лежат в репозитории, `cargo` Node не вызывает. Байткод прелюдии, chai и lodash компилируется **один раз
  за запуск приложения** **[моё решение]** (а не при сборке): он всегда сделан тем же движком, что его
  загружает. Первая компиляция — ~5,4 мс прелюдия и ~8,6 мс chai. chai и lodash грузятся при первом обращении.
- Песочница: нет файловой системы, `fetch`, `XMLHttpRequest`, `process`, `require('fs')`; сеть — только через
  `pm.sendRequest`. Тело-файл и файловые части в `pm.sendRequest` вырезаются; pre-request не может сделать тело
  запроса файлом, binary, form-data или GraphQL. Объект примитивов хоста скрипту не виден, а прямой вызов
  примитива не даёт ничего сверх `pm.*`: пределы и запреты проверяет Rust.
- Пределы (настраивается только время):

  | Предел | Значение | При превышении |
  |---|---|---|
  | Время исполнения JavaScript одного скрипта (ожидание `pm.sendRequest` и таймеров не считается) | 10 с; настройка 100…600 000 мс | ошибка скрипта «превышен предел времени» |
  | Суммарное ожидание таймеров одним скриптом | 60 с | то же |
  | Ожидание ответа `pm.sendRequest` | общий таймаут запроса | ошибка в callback / отклонённый Promise |
  | Память движка на скрипт | 128 МиБ | ошибка «превышен предел памяти» |
  | Стек JavaScript | 8 МиБ (поток — 16 МиБ) | `RangeError` в скрипте |
  | Тело ответа, доступное скрипту | 10 МиБ | `pm.response.text()` / `json()` бросают ошибку |
  | Консоль за отправку | 1000 строк и 1 МиБ; строка — 10 000 символов | лишнее отбрасывается, пометка «вывод обрезан» |
  | Тесты за фазу | 1000; имена и ошибки вместе — 256 КиБ | ошибка скрипта |
  | Значение переменной из скрипта | 1 МиБ | `set` бросает ошибку, которую скрипт может поймать |
  | Переменные и журнал изменений за фазу | 16 МиБ; 10 000 изменений | ошибка «превышен предел памяти» |
  | `pm.sendRequest` | 50 на скрипт; запрос — 10 МиБ; очередь — 32 МиБ | ошибка |

- **Сторож** **[моё решение]** (решения № 37 и 38 плана этапа 2): обработчик прерывания QuickJS не вызывается
  внутри части нативных циклов (`[].reverse.call({length: 2**53-1})`). Такой скрипт через 2 с сверх предела
  времени (или после Cancel) бросается: отправка получает ошибку, а поток доживает сам и к хосту больше не
  обращается; он занимает ядро процессора и до 128 МиБ, пока не кончит или до закрытия программы. Одновременно
  брошенных потоков — не больше 4; дальше скрипты не исполняются («сбой движка») до перезапуска.
- Изменения переменных из скрипта записываются в хранилище один раз, когда отправка завершилась (в том числе
  ошибкой или отменой), включая сделанные до ошибки в скрипте — так ведёт себя движок Postman (сверено по
  исходникам `postman-runtime` 7.56.3). Значение в пределах одной отправки сохраняет тип; в базу пишется
  строка `String(value)`, поэтому в следующей отправке число вернётся строкой.
- В test-скрипте `pm.request` — **отправленный** запрос: переменные подставлены, заголовок авторизации есть;
  автоматических заголовков (`User-Agent`, `Host` …) в нём нет (решение № 40). В pre-request — запрос как
  введён, изменения уходят в запрос.
- `pm.sendRequest` идёт через тот же `HttpEngine` (общие cookies, прокси, проверка сертификата); `{{переменные}}`
  в нём **не подставляются**, как в Postman (решение № 28); запросы одного скрипта идут по очереди; в историю
  он не пишется.
- Одиночный суррогат в тексте, уходящем из скрипта, заменяется на U+FFFD.

### API первой версии
Полный список — таблица «API в первой версии» плана этапа 2 и её итог в разделе 5 документа
`2026-11-17-stage2-scripts-results.md`. Коротко: переменные четырёх областей, `pm.info`, `console.*`,
`pm.response` и утверждения `pm.response.to.*`, `pm.test` (синхронные и асинхронные), `pm.expect` (chai 4.4.1),
таймеры и `async/await`, `pm.sendRequest`, `pm.request`, старый API (`postman.*`, `tests[...]`,
`responseBody` …), `require('lodash')` — lodash 4.18.1 (глобальный `_` — тоже lodash 4; в Postman — lodash 3),
`atob` / `btoa`.

В первой версии есть и то, что эта спека относила к «позже» **[моё решение]** (решение № 36, принято
владельцем): `pm.execution.skipRequest()` — отменяет одну отправку и не требует Runner;
`pm.execution.setNextRequest`, `pm.iterationData`, `pm.visualizer` — пустые, чтобы старые скрипты не падали.

У владельца (одна коллекция) встречаются только `pm.collectionVariables.set`, `responseBody` и `JSON.parse`;
поднимать из «позже» ничего не понадобилось.

Позже: `crypto-js`, `moment`, `ajv`, `tv4`, `uuid`, `cheerio`, `xml2js`, `pm.cookies`, `pm.vault`,
`pm.require`, faker-переменные, Web Crypto, действие `setNextRequest` и данные `pm.iterationData` (вместе с
Runner). Вызов неподдержанного бросает `<имя> is not supported in RequestMaster`.

- Сохранение **[моё решение]**:
  - сразу, без Ctrl+S: структура дерева (создание, переименование, перемещение, удаление), окружения и
    переменные, изменения переменных из скриптов, состояние окна;
  - черновиком до Ctrl+S: содержимое запроса и содержимое редактора коллекции/папки. Вкладка с черновиком
    помечена точкой; Send отправляет черновик. Черновики хранятся в `app_state` и переживают перезапуск.
  - закрытие окна (план 2 части 3): вопроса о несохранённых вкладках нет — черновики и состояние окна
    записываются и возвращаются при следующем запуске. Вопрос «Не удалось сохранить состояние. Закрыть всё
    равно?» показывается только при сбое записи черновика, состояния окна или окружения.
  Изменение переменной из скрипта (этап 2): окно получает дельту вместе с ответом и применяет её к открытым
  вкладкам. Окружения сохраняются сразу, поэтому открытый редактор окружения просто обновляется. Переменные
  коллекции — часть черновика вкладки коллекции **[моё решение]** (решение № 14 плана этапа 2): дельта
  применяется и к сохранённой копии, и к черновику, так что несохранённые правки целы, а Ctrl+S не возвращает
  старое значение. Перед отправкой окно дописывает несохранённые правки вкладок активного окружения и Globals;
  несохранённый скрипт вкладки коллекции или папки не исполняется до Ctrl+S, скрипт запроса — исполняется.
- Настройки скриптов (этап 2): «Выполнять скрипты» и «Лимит времени скрипта, мс» в окне «Настройки». Когда
  скрипты выключены или коллекции не разрешены, отправка идёт без них с предупреждением; у предупреждения о
  коллекции — кнопка «Разрешить».
- Редактор скриптов (этап 2): автодополнение `pm.*`, `console`, `postman.*` по статическому списку.
- Клавиши: Ctrl+Enter — отправить, Ctrl+S — сохранить, Ctrl+T / Ctrl+W — вкладки, Ctrl+L — фокус в URL,
  Ctrl+F — поиск в ответе.

### Переменные в интерфейсе
`{{var}}` подсвечивается в URL, заголовках, теле; цвет показывает область. По наведению — итоговое значение
и область. Неразрешённая переменная — красное подчёркивание и счётчик у кнопки Send; отправку не блокирует.
Автодополнение после `{{`.

Уточнения плана 2 части 3 **[моё решение]**:
- подсветка есть в URL, Params, Headers и теле (raw, urlencoded, текст form-data); её нет на вкладке Auth,
  в скриптах и в редакторе окружений; сегмент `/:id` не подсвечивается;
- значения и области даёт ядро (команда `variables_in_scope`); значение секретной переменной и переменной,
  которая на неё ссылается, в окно не передаётся — в подсказке и в списке маска;
- правило счётчика у Send: окно считает имена `{{…}}` во включённых местах черновика этого запроса, которых нет
  среди переменных области. Переменные унаследованного auth и вложенные `{{a{{b}}}}` счётчик не видит —
  предупреждение после отправки может назвать больше.

### История (часть 3 этапа 1)
- Раздел «История» в сайдбаре: записи новые сверху, сгруппированы по дням («Сегодня», «Вчера», дата вида
  `13.11.2026`). Строка: время `ЧЧ:ММ:СС` по местному времени, метод цветом, имя запроса (адрес — в подсказке),
  справа статус цветом и время в мс; у неудачной отправки — вид ошибки («отменён», «нет соединения»,
  «таймаут»…) вместо статуса. Показаны первые 100 записей, «Показать ещё» догружает по 100.
- Список обновляется при открытии раздела и после каждой отправки; запись отменённой отправки появляется,
  когда отправка действительно остановилась.
- Щелчок по записи открывает вкладку только для чтения «История · <имя>» на всю рабочую область: сверху — когда
  отправлено, метод и адрес, статус, время, размер; слева «Запрос», справа «Ответ» — заголовки таблицей, тело
  в редакторе кода, Pretty / Raw у каждого тела. Пометки «Тело обрезано до 1 МБ» и «Ответ не текстовый — в
  истории не хранится»; ошибка и предупреждения отправки — как в панели ответа.
- «Открыть запрос» открывает вкладку исходного запроса; если запрос удалён — кнопка неактивна, запись остаётся.
- «Очистить историю» — с вопросом; открытые вкладки истории закрываются.
- Что и сколько хранится — раздел 5 (таблица `history`).

даёт 16–24 мс, и сравнение `duration` с 16 мс проваливалось бы без вины кода.

## 11. Безопасность

- Скрипты изолированы (раздел 8) и исполняются только при Send, только в ядре (окно текст скрипта не исполняет,
  CSP не менялась) и только если включено «Выполнять скрипты» и коллекции дано согласие. Согласие хранится в
  `app_state` (ключ `scripts_allowed`, список id коллекций). **[владелец]** (2026-11-18): по умолчанию
  разрешено всё, в том числе импортированные коллекции; согласие — способ запретить скрипты отдельной
  коллекции (без согласия не исполняется ни одна строка).
- Что скрипт может: читать и менять переменные четырёх областей, включая секретные; в pre-request менять
  метод, адрес, заголовки и текстовое тело; читать ответ; слать HTTP(S)-запросы на любой адрес, включая
  `localhost` и внутреннюю сеть, с общими cookies и прокси (`pm.sendRequest`); писать в консоль.
- Чего скрипт не может: читать и писать файлы; выходить в сеть иначе, чем через `pm.sendRequest`; видеть
  процесс и окружение ОС; трогать окно; сохранять что-либо, кроме значений переменных; пережить отправку
  (исключение — поток, брошенный сторожем: он считает дальше, но к хосту обратиться не может). Пределы —
  таблица раздела 8; все их проверяет Rust, подмена встроенных объектов скриптом их не снимает.
- Консоль скриптов в историю не пишется; в историю попадают имена тестов и тексты их ошибок. Значения,
  записанные скриптом в переменные (токены), лежат в базе открыто и уходят в экспорт.
- Тексты лицензий встроенных библиотек движка — `THIRD-PARTY-LICENSES.txt`, ресурс установщика.
- Preview HTML — изолированный iframe; строгая CSP; интерфейсу закрыт доступ к внешним доменам.
  CSP окна (план 2 части 3, `src-tauri/tauri.conf.json`): `default-src 'self'; script-src 'self'; style-src 'self';
  img-src 'self' data:; font-src 'self'; connect-src ipc: http://ipc.localhost; object-src 'none'; base-uri 'none';
  form-action 'none'; frame-src 'none'; worker-src 'none'`. `'unsafe-inline'` для стилей снят: стили редактора
  кода проходят по nonce, который подставляет Tauri **[моё решение]**; в разметке нет статических атрибутов
  `style="…"` (закреплено тестом). В живом окне **[проверить]** — раздел 2 списка проверки плана 2; откат — две
  строки `tauri.conf.json`.
- Значение секретной переменной в окно для подсказок не передаётся (раздел 9).
- Секреты в первой версии не шифруются (локальный файл в профиле пользователя) — осознанное упрощение.
- Никаких сетевых обращений, кроме запросов пользователя: без телеметрии и автообновления.

## 13. Проверка качества

- Ядро: модульные тесты на каждый crate; для `rqm-postman` — тесты «импорт → экспорт» на корпусе реальных файлов;
  для `rqm-vars` — таблица случаев подстановки; для `rqm-script` — набор скриптов-образцов с ожидаемым результатом;
  для `rqm-http` — тесты против локального тестового сервера.
- Приёмка первой версии: 3–5 реальных коллекций владельца импортируются; запросы уходят; скрипты получения токена
  отрабатывают; экспорт открывается в Postman без потерь.
